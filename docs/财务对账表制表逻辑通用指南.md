# 财务对账表制表逻辑通用指南

> 本文件用于记录财务对账表的通用制表逻辑、字段设计、匹配规则、异常处理方法和示例说明。  
> 内容应保持通用，不绑定某一个具体项目、客户、供应商或文件名。

## 1. 制表目标

财务对账表的核心目标是：

1. 将不同来源的财务数据放在同一套口径下进行核对。
2. 判断每一笔业务是否已经匹配、是否存在差异。
3. 找出差异原因，并形成可追踪、可复核的处理记录。
4. 支持按日期、客户、供应商、项目、账户、科目等维度汇总。

常见对账场景包括：

- 银行流水与账面收付款记录对账。
- 发票清单与收付款记录对账。
- 订单、合同、发票、收款之间的勾稽核对。
- 供应商应付账款与实际付款对账。
- 客户应收账款与实际回款对账。
- 多账户、多主体、多项目之间的资金往来核对。

## 2. 通用数据来源

对账表通常会涉及多个来源表。不同场景下名称可以变化，但逻辑上一般分为以下几类：

| 数据类型 | 常见内容 | 作用 |
| --- | --- | --- |
| 业务发生数据 | 订单、合同、项目记录、费用申请 | 说明业务为什么发生 |
| 财务确认数据 | 发票、应收、应付、记账凭证 | 说明财务上确认了什么 |
| 资金流水数据 | 银行流水、支付平台流水、现金记录 | 说明实际收付了多少钱 |
| 辅助信息数据 | 客户、供应商、项目、账户、部门、人员 | 用于匹配、归类和汇总 |

## 3. 通用字段设计

### 3.1 基础字段

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| 日期 | 业务发生、开票、入账或收付款日期 | 2026-08-10 |
| 对方名称 | 客户、供应商、付款方或收款方 | 某客户、某供应商 |
| 摘要 / 备注 | 原始记录中的说明文字 | 项目服务费、货款、报销款 |
| 金额 | 当前记录对应的金额 | 10,000.00 |
| 收支方向 | 收入、支出、应收、应付等 | 收入 |
| 账户 / 主体 | 银行账户、公司主体或核算主体 | 基本户、一般户 |
| 业务类型 | 货款、服务费、押金、退款、手续费等 | 服务费 |
| 项目 / 部门 | 如果需要按项目或部门核算，则保留此字段 | A 项目 |

### 3.2 对账字段

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| 匹配状态 | 是否已匹配 | 已匹配、需要复核、未匹配、异常 |
| 匹配编号 | 将互相对应的记录归为同一组 | M20260810001 |
| 匹配依据 | 说明为什么认为两边数据匹配 | 金额一致 + 对方名称一致 + 日期接近 |
| 差异金额 | 两边金额差额 | 100.00 |
| 复核类型 | 说明为什么需要人工复核 | 规格需复核、日期需复核、日期规格需复核 |
| 差异原因 | 差异产生的解释 | 手续费、部分付款、跨期入账 |
| 处理建议 | 后续应如何处理 | 补录发票、确认尾款、调整账务 |
| 复核人 / 复核日期 | 人工确认记录 | 财务复核、2026-08-10 |

## 4. 对账基本逻辑

### 4.1 先统一口径

在开始匹配前，应先统一以下口径：

1. 日期格式统一，例如全部使用 `YYYY-MM-DD`。
2. 金额格式统一，例如收入为正数、支出为负数，或使用单独的收支方向字段。
3. 对方名称尽量标准化，避免同一对象出现多个写法。
4. 去除无意义空格、特殊符号和明显的格式差异。
5. 明确是否含税、是否含手续费、是否按发生制或收付实现制核对。

示例：

| 原始对方名称 | 标准化名称 |
| --- | --- |
| XX有限公司 | XX 有限公司 |
| XX公司 | XX 有限公司 |
| XX 有限公司（付款） | XX 有限公司 |

### 4.2 再建立匹配规则

常见匹配规则可以从严格到宽松分层：

#### 规则 1：完全匹配

满足以下条件时，可认为高度可信：

- 金额完全一致。
- 对方名称一致或高度相似。
- 日期一致或在允许范围内。
- 摘要、订单号、发票号、合同号等关键字一致。

示例：

| 账面记录 | 银行流水 | 判断 |
| --- | --- | --- |
| 2026-08-01，应收服务费，10,000 元，客户 A | 2026-08-01，客户 A 转入 10,000 元 | 已匹配 |

#### 规则 2：日期容差匹配

资金到账日期和账面日期可能不完全一致，可设置日期容差。

常见容差：

- 同日匹配。
- 前后 1 天。
- 前后 3 天。
- 同一自然月内。

示例：

| 账面日期 | 流水日期 | 金额 | 判断 |
| --- | --- | --- | --- |
| 2026-08-01 | 2026-08-03 | 5,000 | 若允许 3 天容差，则可匹配 |

#### 规则 3：一对多匹配

一笔账面记录可能对应多笔实际收付款。

示例：

| 账面应收 | 实际收款 | 判断 |
| --- | --- | --- |
| 客户 A 应收 10,000 元 | 8 月 1 日收 6,000 元，8 月 5 日收 4,000 元 | 一对多，合计已匹配 |

#### 规则 4：多对一匹配

多笔账面记录可能合并成一笔付款或收款。

示例：

| 账面记录 | 实际流水 | 判断 |
| --- | --- | --- |
| 发票 1：3,000 元；发票 2：7,000 元 | 客户 A 一次转入 10,000 元 | 多对一，合计已匹配 |

#### 规则 5：部分匹配

当金额只匹配一部分时，应标记为部分匹配，并记录未结余额。

示例：

| 应收金额 | 已收金额 | 未收金额 | 状态 |
| --- | --- | --- | --- |
| 10,000 | 6,000 | 4,000 | 部分匹配 |

### 4.3 需要复核的匹配能力

对账时不能只分成“已匹配”和“未匹配”。实际业务中，经常会出现 **数量或金额能对上，但某些关键字段不完全一致** 的情况。

这类记录不应该直接算作普通的“已匹配”，也不应该简单归为“未匹配”，而应标记为：

```text
需要复核
```

或在匹配状态中进一步说明复核原因，例如：

```text
已匹配/规格需复核
已匹配/日期需复核
已匹配/日期规格需复核
```

#### 适用场景

| 场景 | 判断 | 建议状态 |
| --- | --- | --- |
| 数量/金额一致，但规格名称不完全一致 | 可能是简称、别名、系统名称和业务名称不同 | 已匹配/规格需复核 |
| 数量/金额一致，但日期不一致 | 可能是送货日期和系统入库日期跨日 | 已匹配/日期需复核 |
| 数量/金额一致，但规格和日期都不完全一致 | 需要人工重点确认 | 已匹配/日期规格需复核 |
| 同一个货号、送货单号能对上，但规格文字不一致 | 可能是名称维护差异 | 已匹配/规格需复核 |
| 能找到候选记录，但数量不一致 | 不应直接匹配 | 未匹配或异常 |

#### 使用原则

1. “需要复核”是一种中间状态，用于保留机器判断结果，同时提醒人工确认。
2. 只有当核心数量或金额能对上时，才可以使用 `已匹配/xxx需复核`。
3. 如果数量或金额对不上，不应标记为已匹配，应保留为 `未匹配` 或 `异常`。
4. 匹配依据中必须写清楚为什么需要复核，例如：

```text
同送货单号+同货号+数量一致，但规格名称不完全一致，需人工复核。
```

5. C 表中仍要保留 B 表原始字段，方便复核人员判断是否确实可以确认。

这样做的目标是避免两种错误：

- 把有疑点的记录直接当成完全匹配。
- 把实际可对应、但字段写法不同的记录直接当成未匹配。


| --- | --- | --- |
| 金额差异 | 两边金额不一致 | 检查手续费、折扣、退款、尾款 |
| 日期差异 | 入账日期与流水日期不同 | 判断是否跨期或到账延迟 |
| 名称差异 | 对方名称写法不同 | 建立名称映射表 |
| 缺少账面记录 | 有资金流水但账上没有记录 | 补录业务或凭证 |
| 缺少资金流水 | 账上有应收应付但未实际收付 | 标记未收或未付 |
| 重复记录 | 同一笔业务被重复录入 | 删除或冲销重复项 |
| 跨期差异 | 业务和资金分属不同期间 | 单独列示跨期项目 |
| 手续费差异 | 第三方或银行扣费导致差额 | 单独确认手续费科目 |

## 6. 推荐表结构

### 6.1 明细对账表

| 字段 | 用途 |
| --- | --- |

| 标准对方名称 | 用于统一匹配 |

## 7. 常用公式思路

> 具体公式可根据 Excel、WPS、Google Sheets 或数据库工具调整。

### 7.1 差异金额

```text
差异金额 = 账面金额 - 实际流水金额
```

示例：

```text
账面金额 10,000，实际到账 9,990
差异金额 = 10,000 - 9,990 = 10
差异原因可能是手续费
```

### 7.2 未收 / 未付金额

```text
未结金额 = 应收或应付金额 - 已收或已付金额
```

示例：

```text
应收 20,000，已收 15,000
未收金额 = 5,000
状态 = 部分匹配
```

### 7.3 匹配状态判断

```text
如果差异金额 = 0，且日期、名称、编号等关键字段都满足严格规则，则为“已匹配”
如果差异金额 = 0，但日期、规格名称、编号等关键字段存在不完全一致，则为“需要复核”
如果差异金额 ≠ 0 且已收/已付金额不为 0，则为“部分匹配”或“需要复核”
如果没有找到对应记录，则为“未匹配”
如果存在重复、金额异常或无法解释差异，则为“异常”
```

## 8. 建议的处理流程

1. 收集所有原始数据。
2. 备份原始数据，不直接覆盖。
3. 统一日期、金额、名称、收支方向等口径。
4. 建立辅助映射表，例如客户名称映射、供应商名称映射、业务类型映射。
5. 先做严格匹配。
6. 再做日期容差、一对多、多对一等宽松匹配。
7. 对未匹配和异常记录进行人工复核。
8. 标记差异原因和处理建议。
9. 生成明细表和汇总表。
10. 定期复核规则，避免历史差异重复出现。

## 10. 实操经验记录：A 表生成 C 表的第一步

### 10.1 第一步目标

在使用 A 表、B 表生成最终 C 表时，第一步不是立即做匹配，而是先把 **A 表完整复制成 C 表的初始底稿**。

本步骤目标：

1. 以 A 表为基础生成新文件 C 表。
2. 保留 A 表原有的明细内容、样式、颜色、边框和基本结构。
3. 取消 A 表中的合并单元格。
4. 将合并单元格中的日期内容复制/填充到原本空白的明细行。
5. 将日期显示为业务人员可读的格式，例如 `7月1日`，而不是 Excel 日期序列号。
6. 表头统一显示为 `七月`。
7. 取消原表中的单元格底色，使 C 表底色保持干净，方便后续增加新的对账标记。

### 10.2 操作流程

#### 步骤 1：复制 A 表生成 C 表

先将 A 表原文件完整复制一份，命名为 C 表。

这样做的原因是：

- C 表需要继承 A 表的原始版式。
- 后续对账字段、B 表匹配结果、差异列等都可以在 C 表基础上继续增加。
- 避免直接修改 A 表原始文件。

#### 步骤 2：取消合并单元格

A 表中日期列通常存在合并单元格，例如：

```text
7月1日  对应多行明细
7月2日  对应多行明细
7月3日  对应多行明细
```

在视觉上看是每一组明细都有日期，但在数据层面，只有合并区域左上角单元格真正有值，其他行是空的。

生成 C 表时，需要取消这些合并单元格。

#### 步骤 3：把合并单元格内容填充到每一行

取消合并后，原本合并区域下面的行会变成空白。

需要把原合并单元格左上角的日期复制到该合并区域内每一行，使每条明细都带有自己的日期。

处理前：

| 日期 | 商品 | 数量 |
| --- | --- | --- |
| 7月1日 | 商品 A | 419 |
| 空 | 商品 A | 462 |

处理后：

| 日期 | 商品 | 数量 |
| --- | --- | --- |
| 7月1日 | 商品 A | 419 |
| 7月1日 | 商品 A | 462 |

#### 步骤 4：日期格式转换

如果使用程序读取 Excel，日期可能会被读成 Excel 日期序列号，例如：

```text
46204
46205
46206
```

这些数字不是业务人员要看的格式，需要转换为：

```text
7月1日
7月2日
7月3日
```

因此，填充日期后还要检查显示格式，确保 C 表中日期列最终是 `7月X日` 这种格式。

#### 步骤 5：表头处理

表头取消合并后，表头文字统一为：

```text
七月
```

注意：表头是月份标题，不参与明细匹配。

#### 步骤 6：取消单元格底色

A 表中可能用黄色、灰色等底色标记不同区域或商品行。

生成 C 表第一步时，需要把这些原始底色取消掉，使 C 表保持干净底稿。

这样做的原因是：

- 原表底色通常只是原始表的视觉标记，不一定适合对账结果表。
- 后续 C 表还要增加匹配状态、差异、异常等新标记，保留旧底色容易干扰判断。
- 清除底色后，后续可以重新按照对账结果统一设置颜色规则。

注意：取消的是单元格填充底色，边框、文字、数值等内容应保留。

### 10.3 本步骤遇到的坑

#### 坑 1：只取消合并单元格，不等于每行都有日期

Excel 中合并单元格看起来覆盖多行，但真实数据只存在于左上角单元格。

如果只是取消合并，不做填充，下面的行会变成空白，后续按日期匹配 B 表时会丢失日期依据。

正确做法：

```text
取消合并单元格后，必须把原合并区域的值复制到区域内每一行。
```

#### 坑 2：日期会变成 Excel 序列号

程序处理 Excel 日期时，可能把 `7月1日` 显示成 `46204`。

原因是 Excel 内部用数字存储日期，`46204` 这类数字其实代表某一天。

如果不转换，C 表会出现不符合业务阅读习惯的数据。

正确做法：

```text
将 Excel 日期序列号转换为“月 + 日”的文本显示格式，例如 7月1日。
```

#### 坑 3：填充日期时要保留格式

日期列原来可能有黄色底色、居中、边框等格式。

填充空行时，如果只填充值，不复制样式，C 表视觉上会不一致。

正确做法：

```text
复制日期值时，同时尽量保留原单元格的样式、边框、填充色和对齐方式。
```

#### 坑 4：不能直接覆盖 A 表

A 表是原始输入表，应保持不动。

正确做法：

```text
先复制 A 表生成 C 表，再在 C 表上做取消合并、填充日期、增加对账字段等处理。
```

### 10.4 第一步完成标准

第一步完成后，C 表应满足：

1. C 表是从 A 表完整复制出来的。
2. A 表原始文件未被修改。
3. C 表中不再有影响明细处理的合并单元格。
4. 每一条明细行都有对应日期。
5. 日期显示为 `7月1日`、`7月2日` 这种格式。
6. 表头显示为 `七月`。
7. 原有商品、数量、单价、金额等字段保持不变。
8. 原有颜色、边框等主要样式尽量保持不变。

## 11. 实操经验记录：C 表与 B 表匹配的第二步

### 11.1 第二步目标

第一步完成后，A 表已经不再参与后续处理。第二步开始使用 **C 表与 B 表进行匹配**。

本步骤目标：

1. 从 C 表逐行读取明细。
2. 根据 C 表日期、规格名称、数量，在 B 表中查找对应记录。
3. 当 C 表 C 列为正数时，匹配 B 表中的入库数据。
4. 将 B 表匹配到的数量、单价、金额写入 C 表指定列。
5. 如果一条 C 表记录对应 B 表多行，需要在 C 表中插入附加行，逐行展示 B 表数据。

### 11.2 使用字段

#### C 表字段

| C 表列 | 含义 | 用途 |
| --- | --- | --- |
| A列 | 日期 | 与 B 表 `系统出入库时间` 判断是否同一天 |
| B列 | 商品 / 规格名称 | 与 B 表 `规格` 判断是否同一个商品 |
| C列 | 数量 | 当为正数时，用于匹配 B 表入库数量 |
| D列 | 单价 | 保留 A 表原始单价 |
| E列 | 金额 | 保留 A 表原始金额 |

#### B 表字段

| B 表列 | 字段名 | 用途 |
| --- | --- | --- |
| E列 | 仓库 | 匹配成功后保留到 C 表，表头统一使用 `仓库`；用于追溯系统仓库、区分配货仓/贴单仓/外协仓等仓库来源 |
| F列 | 系统出入库时间 | 提取日期，与 C 表 A列匹配；匹配成功后也要保留到 C 表，方便追溯系统入库/出库时间 |
| G列 | 单据编号 | 匹配成功后保留到 C 表，表头保持 `单据编号` |
| H列 | 货品编号 | 匹配成功后保留到 C 表，表头保持 `货品编号` |
| I列 | 货品名称 | 匹配成功后保留到 C 表，表头保持 `货品名称` |
| J列 | 规格 | 与 C 表 B列匹配；匹配成功后保留到 C 表，表头保持 `规格` |
| K列 | 入库数量 | 与 C 表 C列匹配 |
| L列 | 入库成本单价 | 匹配成功后写入 C 表 |
| M列 | 入库成本金额 | 匹配成功后写入 C 表 |
| N列 | 出库数量 | 第三步可能使用 |
| O列 | 出库成本单价 | 第三步可能使用 |
| P列 | 出库成本金额 | 第三步可能使用 |

### 11.3 基础匹配规则

从 C 表第一条明细开始逐行处理。

当 C 表 C 列为正数时，表示当前行需要匹配 B 表的入库数据：

```text
C表 C列 > 0  →  匹配 B表 K列：入库数量
```

匹配时需要同时满足：

1. C 表 A列日期与 B 表 `系统出入库时间` 属于同一天。
2. C 表 B列商品名称与 B 表 `规格` 属于同一个名字。
3. C 表 C列数量与 B 表 `入库数量` 能够对上。

### 11.4 单行匹配

如果 B 表中存在一行满足：

```text
同一天 + 同规格 + B表K列入库数量 = C表C列数量
```

则认为该 C 表行已匹配。

匹配后，C 表中填写：

| C 表列 | 填写内容 | 来源 |
| --- | --- | --- |
| 匹配状态列 | 匹配状态 | 自动判断，例如 `已匹配` |
| 匹配依据列 | 匹配依据 | 自动说明匹配规则 |
| 仓库 | 仓库 | B 表 E列，表头统一使用 `仓库` |
| 系统出入库时间 | 系统出入库时间 | B 表 F列，表头保持一致 |
| 单据编号 | 单据编号 | B 表 G列，表头保持一致 |
| 货品编号 | 货品编号 | B 表 H列，表头保持一致 |
| 货品名称 | 货品名称 | B 表 I列，表头保持一致 |
| 规格 | 规格 | B 表 J列，表头保持一致 |
| B数量 / 入库数量 | 入库数量 | B 表 K列 |
| B单价 / 入库成本单价 | 入库成本单价 | B 表 L列 |
| B金额 / 入库成本金额 | 入库成本金额 | B 表 M列 |

注意：C 表承接 B 表信息时，`系统出入库时间`、`单据编号`、`货品编号`、`货品名称`、`规格` 这些字段要完整保留，且表头文字应与 B 表保持一致，方便后续筛选、复核和追溯。

### 11.5 多行连续匹配

如果 B 表当前行的入库数量小于 C 表 C列数量，则继续看 B 表下一行。

规则：

```text
如果 B表当前行 K列 < C表C列
则尝试：当前行 + 下一行
如果仍需要，也可以尝试连续三行
```

只要连续 2 行或连续 3 行的入库数量合计等于 C 表 C列数量，就认为匹配成功。

示例：

| C表数量 | B表行 | B表入库数量 | 判断 |
| --- | --- | --- | --- |
| 462 | 第5行 | 449 | 当前行小于 C表数量 |
| 462 | 第6行 | 13 | 449 + 13 = 462，匹配成功 |

### 11.6 多行匹配时的插行规则

当一条 C 表记录对应 B 表两行或三行时，不能把 B 表多行合计后只写在 C 表一行中。

正确做法是：

1. 保留 C 表当前行。
2. 在当前行下面插入附加行。
3. 每一行分别承接 B 表的一行数据。

例如：

```text
C表第3行 对应 B表第5行、第6行
```

处理后：

| C表行 | 对应B表行 | 系统出入库时间 | 单据编号 | 货品编号 | 货品名称 | 规格 | 入库数量 | 入库成本单价 | 入库成本金额 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 第3行 | B表第5行 | B表第5行F列 | B表第5行G列 | B表第5行H列 | B表第5行I列 | B表第5行J列 | B表第5行K列 | B表第5行L列 | B表第5行M列 |
| 第4行 | B表第6行 | B表第6行F列 | B表第6行G列 | B表第6行H列 | B表第6行I列 | B表第6行J列 | B表第6行K列 | B表第6行L列 | B表第6行M列 |

如果对应 B 表三行，则在 C 表当前行下面插入两行。

### 11.7 新增插入行的留空规则

多行匹配时，新增插入的附加行中，C 表 **B-E列要保持空白**。

也就是说：

| C表行类型 | A列 | B-E列 | J-L列 |
| --- | --- | --- | --- |
| 原始C表行 | 保留日期 | 保留原始商品、数量、单价、金额 | 填第一条B表记录的K-M列 |
| 新增插入行 | 可保留日期 | 保持空白 | 填后续B表记录的K-M列 |

这样可以看出：

- 原始 C 表只有一条业务记录。
- 下面新增的行只是为了展开显示 B 表对应的多条记录。
- 不会误以为 C 表原始业务也新增了多条。

### 11.8 B 表信息保留与表头规则

第二步中，C 表需要保留 B 表的关键追溯字段，尤其是下列字段：

```text
仓库、系统出入库时间、单据编号、货品编号、货品名称、规格
```

这些字段从 B 表带入 C 表时，表头要保持和 B 表一致，不要改成含糊的自定义名称。

原因是：

- 后续复核时可以直接按系统字段筛选。
- 可以从 C 表反查 B 表的具体系统记录。
- 可以看出匹配到的是哪一个货品编号、货品名称和规格。
- 避免只写数量、单价、金额后失去 B 表原始上下文。

因此，匹配成功后，C 表除了写入入库数量、入库成本单价、入库成本金额外，还应同步写入：

| C 表表头 | 来源 |
| --- | --- |
| 仓库 | B 表 E列 `仓库` |
| 系统出入库时间 | B 表 F列 `系统出入库时间` |
| 单据编号 | B 表 G列 `单据编号` |
| 货品编号 | B 表 H列 `货品编号` |
| 货品名称 | B 表 I列 `货品名称` |
| 规格 | B 表 J列 `规格` |
| 入库数量 | B 表 K列 `入库数量` |
| 入库成本单价 | B 表 L列 `入库成本单价` |
| 入库成本金额 | B 表 M列 `入库成本金额` |

如果后续第三步处理出库，则数量、单价、金额字段改为承接 B 表 N-P列，但上述 F-J 的追溯字段仍然要保留。

### 11.9 商品名称匹配注意事项

C 表 B列和 B 表 `规格` 字段可能不是完全一致的文本，但业务上代表同一个商品。

常见差异包括：

| 差异类型 | 示例 |
| --- | --- |
| 多余符号 | C表名称末尾有 `*` |
| 全角半角不同 | `＋` 与 `+` |
| 连接符不同 | 有的名称有 `-`，有的没有 |
| 后缀不同 | `站脚款` 与 `站脚` |
| 后缀不同 | `滑轮款` 与 `滑轮` |

因此，匹配前应先做规格名称标准化，再判断是否为同一个名字。

### 11.10 规格、日期等字段需要复核的处理

在 C 表与 B 表匹配时，除了严格匹配，还要支持“需要复核”的能力。

严格匹配通常要求：

```text
同日期 + 同规格 + 数量一致
```

但实际表格中可能出现以下情况：

- A 表使用业务名称，B 表使用系统名称。
- A 表规格是简称，B 表规格更完整。
- A 表送货日期和 B 表系统入库日期不同，但送货单号、货号、数量能对上。
- 同一个货品编号下，规格描述存在细微差异。

这类情况如果核心数量能对上，并且有送货单号、货品编号等辅助依据支撑，可以先标记为：

```text
已匹配/规格需复核
已匹配/日期需复核
已匹配/日期规格需复核
```

但必须注意：

1. 这不是普通的完全匹配，而是带人工复核要求的匹配。
2. 匹配依据中要写清楚触发复核的原因。
3. C 表要保留 B 表原始字段，尤其是仓库、系统出入库时间、单据编号、货品编号、货品名称、规格。
4. 如果数量无法对上，不能使用 `已匹配/xxx需复核`，应保留为 `未匹配` 或 `异常`。

示例：

| A/C 表依据 | B 表依据 | 数量 | 判断 |
| --- | --- | --- | --- |
| 同送货单号 + 同货号 | 规格文字不完全一致 | 数量一致 | 已匹配/规格需复核 |
| 同规格 + 同送货单号 | 日期不同 | 数量一致 | 已匹配/日期需复核 |
| 同货号 + 同送货单号 | 日期、规格均不同 | 数量一致 | 已匹配/日期规格需复核 |
| 同货号 + 同送货单号 | 数量不一致 | 数量不一致 | 未匹配或异常 |

### 11.11 本步骤遇到的坑

#### 坑 1：多行匹配不能只写合计

一开始容易把 B 表两行或三行的数量合计后，直接写入 C 表同一行。

这样虽然数量能对上，但会丢失 B 表原始行的明细关系。

正确做法：

```text
B表匹配到几行，C表就展开几行；每一行对应一条B表记录。
```

#### 坑 2：新增行不能重复填 C 表 B-E列

多行匹配时，新增插入的行只是为了展示 B 表拆分明细，不是新增 C 表原始业务。

如果新增行也复制 C 表 B-E列，会让人误以为 C 表原始业务多了一条。

正确做法：

```text
新增插入行中，B-E列保持空白，只填写用于承接B表的匹配列。
```

#### 坑 3：B 表字段不能只保留数量、单价、金额

如果 C 表只写入 B 表的数量、单价、金额，而没有保留 `系统出入库时间`、`单据编号`、`货品编号`、`货品名称`、`规格`，后续人工复核时会缺少追溯依据。

正确做法：

```text
C表要完整承接B表关键字段：仓库、系统出入库时间、单据编号、货品编号、货品名称、规格、数量、单价、金额，并且表头保持和B表一致。
```

#### 坑 4：入库和出库字段不能混用

第二步中，C 表 C列为正数时，当前规则是匹配 B 表入库数据，即 B 表 K-M列。

但 B 表还有 N-P列，是出库数量、出库单价、出库金额，后续第三步可能会用到。

正确做法：

```text
第二步先明确：正数匹配入库 K-M；不要提前混用 N-P。
```

### 11.11 第二步完成标准

第二步完成后，C 表应满足：

1. 已经不再依赖 A 表。
2. C 表每条正数数量记录，按日期和规格去 B 表查找入库记录。
3. 单行匹配时，C 表 J-L列填写对应 B 表单行 K-M列。
4. 多行匹配时，C 表会在当前行下方插入附加行。
5. 插入行的 B-E列保持空白。
6. 多行匹配时，每一行 J-L列分别填写对应 B 表单行 K-M列。
7. C 表中保留匹配状态、匹配依据和 B 表行号，便于复核。
8. 未匹配记录需要保留，并说明未匹配原因，供下一步继续处理。

### 11.12 插行后的合计公式核查

C 表在匹配 B 表时，如果发生一对多匹配，需要在原 A 表记录下方插入新行。

插入行以后，必须重新核查合计公式和明细金额公式，不能直接沿用 A 表原公式。

原因是：

1. A 表合计行会被插入行推到新的行号。
2. 原来的合计公式可能仍然只统计到旧的明细末行。
3. 原 A 表中如果存在跨行引用或相对引用公式，插行后可能引用错行。
4. C 表新增的 B 表明细行通常不应该重复填入 A 表原始业务列，否则会影响 A 表口径合计。

典型错误示例：

```text
A 表原合计公式：G545 = SUM(G4:G544)
C 表插入多行后，合计行变为 G571
错误公式：G571 = SUM(G4:G544)
正确公式：G571 = SUM(G4:G570)
```

正确处理规则：

1. C 表全部插行完成后，再重新定位 `合计` 行。
2. 合计公式必须按新位置重写，范围为首条明细行到合计行上一行。
3. 数量、金额等 A 表口径汇总列，都要分别重写公式。
4. 金额列如果原明细单元格是公式，优先使用 A 表已计算出的结果值写入 C 表，避免插行后相对引用错位。
5. 插入的 B 表拆分行中，A 表原始业务列保持空白，不参与 A 表口径合计。
6. 金额列宽要足够，避免 WPS / Excel 显示 `########`，影响人工核查。

公式写法按实际表结构调整。

示例：

```text
数量合计 = SUM(E4:E{合计行-1})
金额合计 = SUM(G4:G{合计行-1})
```

如果不同任务的数量列、金额列不在 E列、G列，应按该任务 A 表实际列号改写。

### 11.13 C 表交付前的金额核查

C 表交付前，必须做一次 A 表口径金额核查。

核查目标：

```text
C 表原始业务列的数量合计 = A 表数量合计
C 表原始业务列的金额合计 = A 表金额合计
```

这里的“原始业务列”指从 A 表继承过来的数量、单价、金额等字段，不包括后面追加的 B 表入库、出库或匹配追溯字段。

核查要求：

1. 找到 A 表合计行，记录 A 表数量合计和金额合计。
2. 找到 C 表合计行，确认合计公式已经覆盖到 C 表所有明细行。
3. 重新计算 C 表原始业务列数量和金额。
4. 对比 A 表与 C 表，差额必须为 0。
5. 检查 C 表明细金额列是否还残留不应存在的公式。
6. 检查 C 表金额合计单元格是否能正常显示金额，不能显示为 `########`。

如果发现 A 表和 C 表金额对不上，优先检查：

1. 合计公式是否仍然引用旧范围。
2. 插入行是否错误复制了 A 表数量或金额。
3. 明细金额公式是否因为插行产生相对引用错位。
4. 是否有隐藏行、空白行或合并单元格导致合计范围遗漏。
5. 金额列宽是否过窄，只是显示异常而不是数据异常。
