# Reconciliation Agent 项目结构实现说明

本文档说明本次为“财务对账 C 表生成与反向核查 Agent”所做的项目结构搭建工作，以及每个文件为什么这样设计。

## 一、整体目标

这次不是做一个 MVP 占位项目，而是先把后续可继续深化实现的完整 Agent 工程骨架搭起来。

项目目标是把现有两份规则文档：

- `docs/财务对账表制表逻辑通用指南.md`
- `docs/财务对账表C表制作与反向核查强制规则.md`

转成一个可执行、可扩展、可审计的 Agent 项目结构。

核心原则是：

1. **LLM 不直接改 Excel**：LLM 负责规划、解释、编排和异常处理建议。
2. **Excel 操作由确定性 Python 工具完成**：用 `openpyxl` 处理复制、匹配、标注、公式、视图等动作。
3. **C 表必须从 A 表完整复制生成**：不能破坏 A 表原始业务口径。
4. **B 表本月记录必须反向核查**：每条本月 B 表记录必须被 C 表承接、被标注缺失，或有人工排除依据。
5. **交付前必须验收**：核查失败时 CLI 返回非 0 状态码，避免错误文件被当成可交付结果。

## 二、根目录文件

### `pyproject.toml`

作用：定义 Python 项目元数据、依赖、开发工具和 CLI 入口。

为什么这样做：

- 使用标准 Python 项目配置，方便后续 `pip install -e .[dev]` 安装。
- 引入核心依赖：
  - `anthropic`：Claude API 官方 SDK，用于 Anthropic/Claude 模型适配。
  - `openai`：OpenAI 官方 SDK，同时复用其 OpenAI-compatible 能力接入 DeepSeek、Qwen。
  - `httpx`：用于访问本地 Ollama HTTP API。
  - `openpyxl`：Excel 读写和格式处理。
  - `pydantic`：配置和领域模型校验。
  - `python-dateutil`：日期解析。
  - `rapidfuzz`：规格、品名等模糊匹配。
  - `typer` / `rich`：CLI 命令行和输出展示。
- 配置开发依赖：`pytest`、`ruff`、`mypy`，为后续测试、Lint、类型检查做准备。
- 注册命令：`reconcile-c-table = agent.cli:app`，让项目可以通过命令行运行。

### `README.md`

作用：项目入口说明。

为什么这样做：

- 让使用者快速知道这个项目的定位：财务对账 C 表生成 Agent。
- 明确五条强制原则，避免后续实现偏离业务规则。
- 写明安装、运行方式和目录结构。

## 三、`agent` 包根目录

### `agent/__init__.py`

作用：声明 `agent` 是 Python 包，并定义版本号。

为什么这样做：

- 让项目可以被正常 import。
- 暴露 `__version__`，后续 CLI、日志、报告中可以记录 Agent 版本。

### `agent/cli.py`

作用：命令行入口。

为什么这样做：

- 使用 `typer` 提供清晰的 CLI 参数：A 表路径、B 表路径、对账月份、输出目录、公司规则 profile。
- 增加 LLM 配置参数：`--llm-provider`、`--llm-model`、`--llm-base-url`、`--llm-api-key-env`。
- CLI 不直接处理业务逻辑，也不直接实例化具体模型供应商，只组装 `ReconciliationRunConfig` 并调用 `CTableWorkflow`。
- 根据 `WorkflowResult.accepted` 返回退出码：通过为 0，不通过为 1，方便后续接入自动化流程或 CI。

### `agent/llm.py`

作用：provider-neutral 的 LLM 编排门面。

为什么这样做：

- 不再把项目绑定为 Claude-only，而是通过统一门面支持 Anthropic、OpenAI、DeepSeek、Qwen、Ollama。
- `ReconciliationLLMAgent` 只负责构造业务 prompt，并调用统一 adapter 的 `complete()` 方法。
- 保留 `ClaudeReconciliationAgent` 作为兼容入口，默认仍使用 `claude-opus-5`，避免已有导入失效。
- LLM 只做两类事情：
  - `explain_plan`：解释运行计划。
  - `suggest_repairs`：根据确定性验收失败报告提出修复建议。
- 文件中特意强调：Excel 修改和验证由确定性工具完成，避免 LLM 直接制造或篡改表格。
- provider 特有参数（例如 Claude adaptive thinking、Ollama HTTP payload）被限制在 adapter 内部，不能污染工作流。

## 四、`agent/llm_providers`：模型供应商适配层

这一层是根据“模型接口添加适配 deepseek、ollama、openai、qwen”的要求新增的。

设计原则：业务 workflow 不直接知道各模型供应商 SDK 或 HTTP API 的差异，只依赖统一的 adapter protocol。

### `agent/llm_providers/__init__.py`

作用：统一导出 LLM provider 相关能力。

为什么这样做：

- 对外集中暴露：
  - `AnthropicAdapter`
  - `OpenAIAdapter`
  - `OpenAICompatibleAdapter`
  - `OllamaAdapter`
  - `LLMProviderAdapter`
  - `LLMProviderError`
  - `LLMResponse`
  - `build_llm_adapter`
  - provider 默认配置解析函数
- 让上层只需从一个包导入模型适配能力。

### `agent/llm_providers/base.py`

作用：定义模型适配层的公共协议和响应结构。

为什么这样做：

- `LLMResponse` 统一返回 `text`、`model`、`provider`，避免上层解析不同供应商响应格式。
- `LLMProviderAdapter` 用 Protocol 固定最小接口：`complete(prompt, max_tokens)`。
- `LLMProviderError` 统一包装底层 SDK/HTTP 异常，便于 workflow 或调用方做一致错误处理。

### `agent/llm_providers/factory.py`

作用：根据 `LLMConfig` 构建具体模型 adapter。

为什么这样做：

- 统一维护 provider 默认模型、默认 base URL、默认 API key 环境变量：
  - `anthropic`：`claude-opus-5` / `ANTHROPIC_API_KEY`
  - `openai`：`gpt-4.1` / `OPENAI_API_KEY`
  - `deepseek`：`deepseek-chat` / `DEEPSEEK_API_KEY` / `https://api.deepseek.com`
  - `qwen`：`qwen-plus` / `DASHSCOPE_API_KEY` / DashScope compatible base URL
  - `ollama`：`qwen2.5` / `http://localhost:11434`
- API key 只从环境变量读取，不硬编码在代码里。
- CLI、workflow、LLM 门面都不需要知道具体 provider 的默认值。

### `agent/llm_providers/anthropic_adapter.py`

作用：Anthropic/Claude 适配器。

为什么这样做：

- 使用官方 `anthropic` Python SDK 调用 Claude Messages API。
- 默认模型由 factory 解析为 `claude-opus-5`。
- Claude 专属的 `thinking={"type": "adaptive"}` 只放在 Anthropic adapter 内，不泄漏到 OpenAI-compatible provider。
- 将 Claude text block 响应规范化成 `LLMResponse`。

### `agent/llm_providers/openai_adapter.py`

作用：OpenAI 适配器。

为什么这样做：

- 使用官方 `openai` Python SDK 调用 Chat Completions。
- 支持 `base_url` 覆盖，为兼容接口复用打基础。
- 响应统一解析为 `choices[0].message.content`。
- 不传入 Claude 专属 thinking 参数，避免污染 OpenAI 请求。

### `agent/llm_providers/openai_compatible_adapter.py`

作用：DeepSeek、Qwen 等 OpenAI-compatible provider 的复用适配器。

为什么这样做：

- DeepSeek 和 Qwen 都可以按 OpenAI-compatible API 处理，没必要重复实现一套 Chat Completions 调用。
- 该类继承 `OpenAIAdapter`，只通过 `provider`、`model`、`base_url` 区分供应商。
- 后续如果增加更多兼容 provider，可以继续复用这一层。

### `agent/llm_providers/ollama_adapter.py`

作用：Ollama 本地模型适配器。

为什么这样做：

- Ollama 默认是本地 HTTP 服务，不需要 API key。
- 使用 `httpx` 请求 `/api/chat`，`stream=False`，并把 `max_tokens` 映射为 Ollama 的 `options.num_predict`。
- 同时兼容 `message.content` 和 `response` 两种返回字段。
- 提供 `close()` 关闭内部 HTTP client，避免长期运行时资源泄漏。

## 五、`agent/domain`：领域模型层

领域模型层负责定义业务对象、状态枚举、配置和结果结构。这样做的原因是：后续无论 CLI、Workflow、工具层还是报告层，都应该围绕同一套强类型对象协作。

### `agent/domain/__init__.py`

作用：声明领域模型包。

为什么这样做：

- 保持包结构清晰，方便后续统一导出领域模型。

### `agent/domain/config.py`

作用：定义一次对账运行的配置模型 `ReconciliationRunConfig`，以及 LLM 供应商配置 `LLMConfig`。

为什么这样做：

- 将 A 表路径、B 表路径、对账月份、输出目录、公司规则 profile 等参数集中管理。
- 使用 Pydantic 校验 `reconciliation_month` 格式必须是 `YYYY-MM`。
- `LLMConfig` 集中管理模型供应商配置：
  - `provider`：限定为 `anthropic`、`openai`、`deepseek`、`qwen`、`ollama`。
  - `model`：允许覆盖默认模型。
  - `base_url`：允许覆盖 OpenAI-compatible 或 Ollama 地址。
  - `api_key_env`：指定读取 API key 的环境变量名。
  - `timeout_seconds` / `max_retries`：控制请求超时和重试。
- 提供派生路径：
  - `c_table_path`
  - `marked_b_table_path`
  - `report_path`
- 这样 Workflow 不需要到处拼文件名，避免路径逻辑分散。

### `agent/domain/statuses.py`

作用：定义匹配方向、匹配状态、B 表覆盖状态、缺失类型。

为什么这样做：

- 财务规则中状态非常关键，不能用散落的字符串。
- 用 `StrEnum` 固定状态值，既能在代码里强类型使用，又能直接输出中文状态。
- 覆盖了规则文档要求的核心状态：
  - `已匹配`
  - `已匹配/规格需复核`
  - `已匹配/日期需复核`
  - `已匹配/日期规格需复核`
  - `部分匹配`
  - `未匹配`
  - `零金额需复核`
  - `补发件需复核`
  - `异常`
- 单独定义 `BRecordCoverageStatus`，用于 B 表本月反向核查。

### `agent/domain/schemas.py`

作用：定义表结构和列定义。

为什么这样做：

- B 表的 E:P 列有明确业务含义，必须固定表达。
- `BTableColumns` 用 1 起始列号定义：
  - E 仓库
  - F 系统出入库时间
  - G 单据编号
  - H 货品编号
  - I 货品名称
  - J 规格
  - K 入库数量
  - L 入库成本单价
  - M 入库成本金额
  - N 出库数量
  - O 出库成本单价
  - P 出库成本金额
- `CAppendColumns` 定义 C 表追加的追溯字段，保证写入列名一致。

### `agent/domain/records.py`

作用：定义 A 表记录、B 表记录、匹配候选、缺失 B 表记录。

为什么这样做：

- `ARecord` 保存 A 表原始业务口径：日期、单据、品名、规格、单位、数量、单价、金额、备注、原始值。
- `BRecord` 保存 B 表系统记录，并区分入库字段和出库字段。
- `BRecord.trace_key()` 用于反向核查追溯，保证 B 表关键字段不会丢。
- `MatchCandidate` 表达一个 A/C 行与一个或多个 B 表行的候选匹配，支持后续多行展开。
- `MissingBRecord` 表达 B 表本月记录未被 C 表承接时的缺失标注信息。

### `agent/domain/results.py`

作用：定义验收检查结果和工作流最终结果。

为什么这样做：

- `VerificationCheck` 用来表达每一个交付检查项是否通过。
- `WorkflowResult` 汇总输出文件、验收结果、A/C 合计、B 表覆盖数量等关键指标。
- `to_display()` 用于 CLI 友好输出，避免 CLI 自己拼业务结果。

## 六、`agent/rules`：规则配置层

规则层用于承载默认规则和未来公司差异规则。

### `agent/rules/__init__.py`

作用：声明规则包。

为什么这样做：

- 为后续按公司、供应商或账期扩展规则留位置。

### `agent/rules/default_rules.py`

作用：定义默认对账规则 profile。

为什么这样做：

- 将容差、规格别名、需要移除的规格字符、强制验收开关集中放在规则对象中。
- `MatchingTolerance` 定义日期、金额、数量、规格相似度容差。
- `RuleProfile` 保留强制规则：
  - 反向 B 表覆盖核查必须开启。
  - 公式错误核查必须开启。
  - 视图复位必须开启。
- 公司差异可以覆盖部分规则，但不能降低强制验收标准。

### `agent/rules/registry.py`

作用：规则 profile 加载入口。

为什么这样做：

- Workflow 只调用 `load_rule_profile(company_profile)`，不用关心具体规则文件在哪里。
- 当前提供 default，后续可以注册更多公司规则。

### `agent/rules/README.md`

作用：说明公司规则 profile 的扩展边界。

为什么这样做：

- 明确哪些可以覆盖：列映射、规格别名、日期容差、金额/数量容差、人工排除来源。
- 明确哪些不能关闭：A/C 口径核查、B 表反向覆盖、公式错误、B 表追溯字段。

## 七、`agent/core`：确定性 Excel 处理层

Core 层是整个项目的关键。它负责真实读写 Excel 和执行规则。LLM 不直接做这些动作。

### `agent/core/__init__.py`

作用：声明 core 包。

为什么这样做：

- 把确定性处理能力集中在一个包内，和 LLM 层分离。

### `agent/core/file_detector.py`

作用：识别工作簿角色。

为什么这样做：

- 规则文档中明确：以 `台州` 开头的文件按 B 表处理。
- `WorkbookDetector` 用文件名做初步识别，并给出置信度和原因。
- `assert_expected()` 可在运行前阻止明显传错文件。

### `agent/core/workbook_loader.py`

作用：统一 Excel 读写。

为什么这样做：

- 所有 openpyxl 加载、保存都走同一个适配器。
- 方便后续增加日志、文件锁、备份、只读加载等能力。
- `iter_data_rows()` 统一过滤空行，减少各模块重复代码。

### `agent/core/normalizer.py`

作用：标准化日期、时间、金额、文本、规格。

为什么这样做：

- A/B 表常存在格式不一致：日期格式不同、金额带逗号、规格有空格或别名。
- 匹配前必须把这些差异归一化，但不能覆盖原始值。
- `spec_value()` 使用规则 profile 中的别名和移除 token，服务于规格匹配。

### `agent/core/record_extractor.py`

作用：从 A/B 工作簿中抽取领域记录。

为什么这样做：

- 将 Excel 单元格读取转换成 `ARecord` / `BRecord`。
- B 表按固定 E:P 列读取，符合规则文档。
- A 表目前采用通用首表约定，并保留 `raw_values`，后续可扩展公司级列映射。
- 入库/出库数量用绝对值保存，便于后续负数 C 行匹配 B 表出库字段。

### `agent/core/c_table_builder.py`

作用：从 A 表完整复制生成 C 表初稿。

为什么这样做：

- C 表必须来源于 A 表，不能直接从 B 表生成。
- 生成时做三件事：
  - 展开合并单元格并填充值。
  - 追加 B 表追溯字段表头。
  - 稳定日期显示格式。
- 保留 A 表原始业务列和样式，满足 A/C 原始口径一致要求。

### `agent/core/matcher.py`

作用：A/C 行与 B 表记录的匹配引擎。

为什么这样做：

- 明确区分匹配方向：
  - A/C 数量为正：匹配 B 表入库字段 K:M。
  - A/C 数量为负：匹配 B 表出库字段 N:P。
  - 零数量、零金额、补发件：进入复核，不自动忽略。
- 使用数量、金额、规格、品名、日期综合判断。
- 输出 `MatchCandidate`，后续由 writer 决定如何写入 C 表。

### `agent/core/c_table_match_writer.py`

作用：把匹配结果写回 C 表。

为什么这样做：

- 匹配逻辑和 Excel 写入逻辑分离，便于测试和审计。
- 支持多行匹配展开：
  - 第一条 B 表记录写入原 A/C 行。
  - 后续 B 表记录插入新行。
  - 新插入行的 A 表原始业务列留空，只写 B 表追溯字段。
- 这样符合“多行匹配必须逐行展开，不能只写合计”的强制规则。

### `agent/core/reverse_verifier.py`

作用：B 表本月记录反向覆盖核查。

为什么这样做：

- 强制规则要求每条本月 B 表记录必须处于：已承接、已标注缺失、人工排除之一。
- `current_month_records()` 只抽取对账月份 B 表记录。
- `coverage_statuses()` 根据 C 表匹配结果、缺失标注、人工排除计算每条 B 表记录状态。
- `uncovered_rows()` 找出仍未覆盖的风险行。

### `agent/core/missing_marker.py`

作用：对未被 C 表承接的 B 表记录做缺失标注。

为什么这样做：

- 规则文档要求不能只在报告中说缺失，必须在 B 表副本中明确标注。
- 按入库、出库、零金额等类型生成 `MissingBRecord`。
- 写入 `C表反向核查状态` 和 `C表反向核查说明`，并用颜色标出。

### `agent/core/formula_manager.py`

作用：公式和显示风险检查。

为什么这样做：

- 交付前必须保证公式错误为 0。
- 金额列不能出现 `########` 显示。
- 该模块提供：
  - `formula_error_cells()`
  - `hash_display_risk_cells()`
  - `widen_amount_columns()`
- 后续可以扩展为公式重算、公式区域校验。

### `agent/core/view_manager.py`

作用：交付视图处理。

为什么这样做：

- 规则要求交付时视图复位到 A1，并冻结表头。
- 该模块集中处理 worksheet view，避免散落在 Workflow 中。

### `agent/core/manual_exclusions.py`

作用：人工排除记录模型和加载器。

为什么这样做：

- B 表本月记录如果没有被 C 表承接，也没有标注缺失，只有在存在人工排除依据时才算覆盖。
- `ManualExclusion` 记录 B 表行号、排除原因、审批人、证据。
- `ManualExclusionRegistry` 提供 row set，便于反向核查使用。
- 支持从简单文本文件加载，为后续人工审核流程预留入口。

## 八、`agent/workflows`：工作流层

### `agent/workflows/__init__.py`

作用：导出 `CTableWorkflow`。

为什么这样做：

- 让其他模块可以通过 `from agent.workflows import CTableWorkflow` 使用工作流。

### `agent/workflows/c_table_workflow.py`

作用：端到端 C 表生成与核查流程。

为什么这样做：

- 将多个确定性工具串联成一条完整、可审计的 Agent 执行链。
- 当前流程包括：
  1. 创建输出目录。
  2. 校验 A/B 表角色。
  3. 抽取 A/B 记录。
  4. 从 A 表生成 C 表初稿。
  5. 匹配 A/C 行与 B 表记录。
  6. 写入 C 表追溯字段。
  7. 抽取 B 表本月记录。
  8. 反向核查未覆盖 B 表记录。
  9. 生成 B 表缺失标注副本。
  10. 准备 C 表交付视图和金额列宽。
  11. 运行交付验收。
  12. 写 Markdown 核查报告。
  13. 返回 `WorkflowResult`。
- CLI 只调用这个 workflow，不直接处理 Excel。

## 十一、`agent/tools`：提供给 LLM 的工具层

这一层是后来根据要求“在 tools 文件夹下加入提供给 LLM 操作 Excel 表格的能力”新增和补强的。

设计原则：LLM 可以调用工具，但不能直接获得 openpyxl 工作簿对象，也不能随意覆盖原始文件。

### `agent/tools/__init__.py`

作用：统一导出 tools 包能力。

为什么这样做：

- 对外暴露：
  - `ReconciliationToolbox`
  - `ToolResult`
  - `ExcelToolset`
  - `ExcelToolRequest`
  - `ExcelToolObservation`
  - `ExcelOperationName`
  - `CellWrite`
  - `RowWrite`
  - `RowMark`
  - `FormulaWrite`
  - `ExcelSafetyPolicy`
- 这样 LLM 编排层或后续 Tool Runner 集成可以从一个地方导入。

### `agent/tools/types.py`

作用：通用工具结果封装。

为什么这样做：

- `ToolResult` 统一表达工具是否成功、消息、产物路径、结构化数据。
- 提供 `success()` / `failure()` 工厂方法，减少重复封装。

### `agent/tools/toolbox.py`

作用：Agent 工具箱门面。

为什么这样做：

- 把底层确定性工具包装成更适合 LLM 编排调用的工具接口。
- 当前提供：
  - `identify_workbook()`：识别 A/B/C 表。
  - `build_c_draft()`：从 A 表生成 C 表初稿。
  - `operate_excel()`：执行通用 Excel 操作请求。
- 工具箱内部组合 `WorkbookLoader`、`WorkbookDetector`、`CTableBuilder`、`ExcelToolset`。

### `agent/tools/excel_models.py`

作用：定义 LLM 操作 Excel 的请求和响应模型。

为什么这样做：

- LLM 调工具时必须传结构化请求，不能传自然语言让工具自由发挥。
- `ExcelOperationName` 限定允许操作：
  - `inspect_workbook`
  - `read_range`
  - `write_cell`
  - `write_row`
  - `append_columns`
  - `insert_rows`
  - `copy_row_style`
  - `mark_rows`
  - `set_formula`
  - `reset_view`
  - `save_as`
- `ExcelToolRequest` 是统一请求 envelope。
- `ExcelToolObservation` 是统一返回结果，包含：
  - 是否成功。
  - 输出路径。
  - 变更单元格。
  - 变更行。
  - 表头。
  - 有界预览。
  - 告警。
- `ExcelSafetyPolicy` 定义护栏，例如写操作必须提供 `output_path`、最大读写单元格数量等。

### `agent/tools/excel_toolset.py`

作用：真正执行 LLM-facing Excel 操作。

为什么这样做：

- 它是一个安全、确定性、可审计的 Excel 工具集。
- 支持先 inspect，再明确 output_path 写入，避免 LLM 直接覆盖原文件。
- 关键能力包括：
  - 查看工作簿结构。
  - 读取范围。
  - 写单元格。
  - 写行。
  - 追加列。
  - 插入行。
  - 复制行样式。
  - 标注行。
  - 写公式。
  - 重置视图。
  - 另存为。
- 每次写入后会检查公式错误和 `########` 显示风险，并在 observation 中返回 warnings。
- 这为未来 Claude Tool Runner 或自定义 agent loop 提供了清晰的工具边界。

### `agent/tools/README.md`

作用：说明 LLM Excel tools 的使用方式和边界。

- 记录工具层设计原则。
